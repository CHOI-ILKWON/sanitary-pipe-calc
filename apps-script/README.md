# 라이선스 백엔드 배포 순서

`license.gs` 를 기존 화이트리스트 스프레드시트에 올려서, 체험 발급·만료·구매 신청을 자동으로 처리하게 만든다.

기존 구글폼 응답 시트는 **읽기만** 한다. 지금 결제하신 분들의 접근은 끊기지 않는다
(첫 실행 때 `라이선스` 시트로 `all / paid / 무기한` 으로 자동 이관된다).

## 0. 먼저 알아야 할 것 — 구 방식의 구멍

기존 `Code.gs` 의 `onFormSubmit` 은 폼이 제출되면 **D열에 `"승인"` 을 자동으로 써넣는다.**
그리고 `doGet` 은 D열이 `"승인"` 이면 통과시킨다. 즉 **구글폼 주소를 아는 사람은
입금하지 않아도 앱이 영구히 열린다.** 홍보를 시작하면 폼 주소가 퍼지는 순간 유료 앱이 무료가 된다.

그래서 아래 6단계(폼 통로 차단)를 반드시 해야 한다. 새 시스템만 올리고 폼을 그대로 두면
무료 통로가 계속 열려 있다.

기존 시트 구조(확인됨): `A 타임스탬프 | B 폼문항 | C 구글 이메일 | D 상태 | E (빈칸)`

## 1. 코드 올리기

1. 기존 화이트리스트 **스프레드시트**를 연다.
2. 확장 프로그램 → **Apps Script**
3. 기존 `Code.gs` 내용을 전부 지우고 `license.gs` 내용을 붙여넣는다.
   (기존 스크립트를 남겨두고 싶으면 파일명을 `Code_old.gs` 로 바꿔두면 되지만,
   `doGet` 이 두 개면 충돌하니 **기존 `doGet` 은 반드시 지우거나 이름을 바꿔야 한다.**)
4. 맨 위 `CONFIG` 를 확인한다. `CLIENT_ID` 는 앱의 `index.html` 값과 같아야 한다.

## 2. 시트 준비 (한 번만)

편집기에서 함수 목록에서 **`setup`** 을 선택하고 실행한다.
처음 실행하면 권한 승인 창이 뜬다 — 본인 계정이니 허용하면 된다.

실행 후 스프레드시트에 시트 3장이 생긴다:

| 시트 | 용도 |
|---|---|
| `라이선스` | 권한의 원본. 이메일 × 앱 한 줄씩 |
| `고객` | 회사·연차·직무·**유입경로**·수신동의 |
| `구매신청` | 정식 이용 신청 접수 목록 |

`라이선스` 시트에 기존 구매자가 옮겨졌는지 눈으로 확인한다.
전원 `앱 = sanitary` / `유형 = paid` / `만료일 = 비어 있음(무기한)` 으로 들어간다.

### 전 앱을 열어줄 사람 승격

전 앱을 열어줄 줄을 선택하고 메뉴 **「라이선스 관리」 → 「선택한 줄 → 전 앱(all) 권한으로」**.
두 줄이 붙어 있으면 한 번에 선택해도 된다. 되돌릴 때는 바로 아래 메뉴를 쓴다.

승격된 줄은 `앱` 칸이 `all` 로 바뀌고, 앞으로 유료화하는 앱까지 전부 통과한다.

> 고객 이메일은 코드에 넣지 않는다. `license.gs` 는 깃 저장소에 올라가는 파일이라
> 커밋하면 고객 이메일이 저장소 이력에 영구히 남는다. 권한은 시트에서만 관리한다.

## 3. 웹 앱으로 배포

배포 → **새 배포** → 유형 `웹 앱`

- 실행 계정: **나**
- 액세스 권한: **모든 사용자** ← 이게 아니면 앱에서 호출이 막힌다

배포 후 나오는 `https://script.google.com/macros/s/.../exec` 주소를 복사한다.

> **중요**: 코드를 수정할 때마다 「새 배포」를 해야 반영된다.
> 「배포 관리 → 편집 → 버전: 새 버전」으로 올리면 **주소가 유지**되니 이 방법을 쓰는 게 편하다.
> 새로 배포해서 주소가 바뀌면 앱의 `WHITELIST_API_URL` 도 같이 바꿔야 한다.

## 4. 확인

브라우저에서 배포 주소 뒤에 `?action=ping` 을 붙여 열어본다.

```
https://script.google.com/macros/s/......../exec?action=ping
```

`{"ok":true,"version":"1.0",...}` 가 보이면 정상이다.

이 시점에서 **라이브 앱은 계속 정상 동작한다.** 옛 앱은 토큰 없이 `?email=` 로 조회하는데,
`CONFIG.ALLOW_LEGACY_EMAIL_CHECK` 가 `true` 라서 새 백엔드가 그 요청도 받아준다.
단, 판정 기준이 폼 응답 시트가 아니라 **`라이선스` 시트**로 바뀌었으므로,
2단계에서 기존 승인자가 제대로 옮겨졌는지 확인하는 것이 중요하다.

## 5. 앱 배포

앱(`index.html` + `auth.js`)을 push 한다. 여기까지 오면 새 흐름이 살아난다.
로그인 → 체험 자동 발급 → 만료 → 정식 신청이 전부 앱 안에서 돌아간다.

새 앱이 정상 동작하는 것을 확인하면 `CONFIG.ALLOW_LEGACY_EMAIL_CHECK` 를 `false` 로 바꾸고
다시 배포한다(토큰 없는 조회를 막는다).

## 6. 구 통로 차단 (필수 — 빠뜨리면 무료 통로가 계속 열려 있다)

새 시스템이 정상 동작하는 것을 확인한 **다음에** 한다.

1. **`onFormSubmit` 트리거 삭제**
   Apps Script 편집기 왼쪽 ⏰ 아이콘(트리거) → `onFormSubmit` 트리거 → ⋮ → 삭제
   (코드에서 함수만 지워도 트리거가 남아 있으면 실행 오류 메일이 계속 온다)
2. **구글폼 응답 받기 중지**
   폼 편집 → 응답 탭 → "응답 받기" 토글 끄기.
   설명란에 "이제 앱에서 바로 시작하실 수 있습니다" + 앱 주소를 남겨두면 기존 링크로 온 사람도 흘러온다.
3. 앱의 `PURCHASE_FORM_URL` 은 이미 코드에서 사라졌으니 따로 할 일 없다.

트리거를 삭제하면 그 뒤로는 폼을 제출해도 `"승인"` 이 찍히지 않는다.
이미 `"승인"` 이 찍혀 있던 사람은 2단계에서 「라이선스」로 옮겨졌으니,
**결제 안 한 줄을 그 시트에서 지우면 그때부터 차단된다** (지금까지는 차단할 방법이 없었다).

## 7. 입금 확인 후 정식 전환 (선생님이 하는 유일한 수동 작업)

구매 신청이 들어오면 메일이 온다. 입금을 확인했으면 `라이선스` 시트에서 해당 줄을 클릭한 뒤
상단 **「라이선스 관리」 메뉴**를 쓰면 된다 (셀을 직접 고치지 않아도 된다):

| 메뉴 | 하는 일 |
|---|---|
| 선택한 줄 → 정식 전환 (무기한) | `유형=paid`, `만료일` 비움 |
| 선택한 줄 → 정식 전환 (1년) | `유형=paid`, `만료일`=1년 후 |
| 선택한 줄 → 차단 | `만료일`=어제 (즉시 차단) |

여러 줄을 한 번에 선택해도 된다. 메뉴가 안 보이면 시트를 새로고침한다(`onOpen` 이 실행되어야 생긴다).

**입금이 안 됐으면 아무것도 하지 않으면 된다.** 체험 만료일이 지나면 자동으로 막힌다.
신청 기록은 `구매신청` 시트에 `입금대기` 로 남으니, 나중에 입금하면 그때 전환하면 된다.

**전 앱 팩**을 팔았으면 줄을 새로 추가한다: `이메일 | all | paid | 오늘 | (비움) | 메모`

사용자는 앱을 새로고침하면 바로 정식으로 바뀐다. 따로 안내 메일을 보낼 필요는 없지만,
보내면 재구매·소개로 이어지니 한 줄 회신하는 게 좋다.

## 참고 — 값 규칙

| 칸 | 값 |
|---|---|
| `앱` | `sanitary` `valve` `fire` `hvac` … / `all` = 전 앱 통과 |
| `유형` | `trial` = 체험, `paid` = 정식 |
| `만료일` | 비어 있으면 **무기한** |

## 편집기에서 바로 쓸 수 있는 함수

| 함수 | 하는 일 |
|---|---|
| `setup` | 시트 생성 + 기존 구매자 이관 |
| `listNewsletterSubscribers` | 수신 동의한 사람 목록 (뉴스레터 발송 대상) |
| `reportChannels` | 유입경로별 집계 — 어느 채널이 사람을 데려오는지 |
| `resetMigrationFlag` | 이관을 다시 돌려야 할 때만 |

## 광고성 메일 주의

`고객` 시트의 `수신동의` 가 `Y` 인 사람에게만 발송한다.
다른 앱 구매를 권유하는 내용이 한 줄이라도 들어가면 광고성 정보이고,
사전 동의 + 제목에 `(광고)` 표기가 필요하다(정보통신망법). 버그 수정 안내 같은
순수 서비스 고지는 예외지만, 판매 권유가 섞이는 순간 광고로 본다.
